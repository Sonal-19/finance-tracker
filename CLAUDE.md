# Finance Tracker

Bun workspaces monorepo: `apps/api` (Elysia + Drizzle + Postgres) and `apps/web` (Vite + React 19 + TanStack Router/Query).
Architecture mirrors `~/Developer/Projects/shimlawale-crm`.

- Ports: API **4300**, web **3300** (Vite proxies `/api`). DB: `finance_tracker` on local Postgres.
- Commands: `bun run dev`, `bun run typecheck`, `bun run lint`, `bun run --cwd apps/api db:push | db:seed`.
- Amounts are integers (bigint) in the smallest INR unit everywhere: stored that way, sent by the API that way, and accepted by it that way. The web turns them into text only with `formatAmount` / `formatAmountShort` / `formatSignedAmount` (`lib/format.ts`, `en-IN`, ₹1,23,456.00); forms convert typed rupees with `toAmount` and prefill with `fromAmount`. The API has the same `formatAmount` in `lib/utils/money.ts` for messages/exports, plus `rupees()` for seeds. Currency is INR only.
- Dates: every date field uses `components/common/date-input.tsx` (`DateInput`, shows dd/MM/yyyy, value is `yyyy-MM-dd`); never use `<input type="date">`.
- Dates are date-only `yyyy-MM-dd` strings in `Asia/Kolkata`; Eden is created with `parseDate: false` so they stay strings.
- Every response uses the `ok()` / `fail()` envelope; the web unwraps it with `call()` / `callMsg()` from `src/lib/api.ts`.
- Logged-in routes use `protectedUser` and are grouped in `controllers/index.ts` so its scoped hooks don't hit `/auth/*`.
- Every query must filter by the session `user.id`, never an id from the request body.
- Dev OTP: `123456` is accepted whenever `NODE_ENV !== "production"`. Sign-up asks for an emailed code only while `SYSTEM_CONFIG.AUTH.REGISTRATION_OTP_REQUIRED` is on (default off; `POST /auth/register/send-otp` then `otp` on `/auth/register`); the web reads it from `/api/auth/config`. It can't be switched on in production without SMTP.
- Chart series colours: income `--chart-income` (teal), expense `--chart-expense` (orange), validated for colour-blind separation. Text uses `text-income` / `text-expense` with +/− signs.
- Phones (<768px): bottom tab bar + FAB, forms open in `ResponsiveSheet` (vaul drawer); desktop gets a sidebar and dialogs.
- Foreign currency (USD only for now): the client sends `amount` + `currency: "USD"` (+ optional `fxRate`); the server converts via `fx-service.ts` (open.er-api.com live, frankfurter.dev historical, `FX_FALLBACK_USD_INR` last resort) and stores INR in `amount`, plus `original_amount` / `original_currency` / `fx_rate`. All totals and reports use INR only.
- Split & share (`splits-controller.ts`, `split-service.ts`): people (no accounts), optional groups, splits with per-person shares (`person_id` null = the user), settlements. Balances are between the user and each person only. The user's own share is a normal debit transaction with `split_id` set (cascade-deleted with the split) and is kept in sync by `syncShareTransaction`; edit it via the split, not directly. Share maths lives in `computeShares` (server) and `previewShares` (web) and must stay identical.
- No boolean columns: state is a pgEnum `status` plus a timestamp for when it changed (`accounts.status` + `archived_at`, `recurring_rules.status` active/paused/completed + `paused_at`/`completed_at`, `shared_split_prefs.decision` + `decided_at`), "one of many" is a nullable timestamp with a partial unique index (`accounts.default_since`, `events.active_since`), and two-way choices are enums (`categories.origin`, `splits.own_share`, `users.tagged_expenses`). The API takes and returns the same enums (`status`, `activation`, `ownShare`, `decision`, `taggedExpenses`).
- Performance: `protectedUser` reads the user from `userCacheService` (60s TTL), so every write to `users` must call `userCacheService.set(row)` or `.invalidate(id)`. Session expiry is extended at most hourly. Account balances are one query of correlated subqueries answered by `transactions_account_idx` / `transfers_*_account_idx` (index-only); keep new per-account sums on that pattern. In a single-table drizzle select, columns inside `sql`…` lose their table prefix, so correlated subqueries must spell out `"accounts"."id"`. Every foreign key has an index (partial where the column is mostly null).
- Accounts are the payment methods (UI label "Payment methods"; table, API and code stay `accounts`). There is no separate payment-method enum or column any more: a transaction just has an account. `transactions.account_id` and `recurring_rules.account_id` are NOT NULL; omit `accountId` in the API to use the default account (`resolveAccountId`). Balance = opening + credits − debits − transfers out + transfers in (`accountBalances`). Transfers live in their own table and never appear in income/expense reports. Accounts with history are archived, not deleted.
- Books (`books-controller.ts`, `book-service.ts`): who an entry was for (Personal, Family, Office…). `transactions.book_id` and `recurring_rules.book_id` are NOT NULL (omit `bookId` to use the default book via `resolveBookId`); `splits.book_id` is nullable (null = default book) and tagged users' copies go to their own default book. `books.totals` is `included` (counts in the user's numbers) or `separate` (paid on someone's behalf: shown as spent − received back = outstanding). Reports and budgets must filter with `countedBookCond(userId, bookId?)`: one book when given, else only `included` books; a report scoped to an account or event counts every book. Account balances ignore books. `status` active/archived + `archived_at`, one default per user (`default_since`); books with history are archived, not deleted. The web header's book switcher (`book-store.ts`, `useBookScope`) passes `bookId` to dashboard, transactions, reports and budgets.
- Events: optional `event_id` on transactions and splits. One event per user can be active (`active_since` set); the web form defaults new entries to it; it auto-deactivates after its end date.
- System config: `SYSTEM_CONFIG` (`db/schema/system/system-config.sql.ts`) holds runtime switches (sign-ups open, passkey login, passkeys per user, FX fallback, notice banner). `systemConfigService` loads it at boot beside the token cache and merges the `system_config` row (id 1) over the code defaults; always read `systemConfigService.SYSTEM_CONFIG`, never the raw export. Admins (`users.role = 'admin'`, set with `db:make-admin <email>`) edit it on `/system-config` via `protectedAdmin` routes; logged-out pages get a safe slice from `GET /api/auth/config`. Adding a key: `docs/HOW_TO_ADD_SYSTEM_CONFIG_FIELD.md`.
- Passkeys (`passkey-service.ts`, `@passwordless-id/webauthn`): any user can add passkeys in Settings (`/api/passkeys/*`) and sign in with one (`/api/auth/passkey/login/*`), which calls the same `startSession` as password login. Challenges are in-memory and one-time-use. `RP_ID` is `ft.u4.lol` in prod and `localhost` in dev; a passkey only works on the hostname it was created on.
- Usernames & tagging: `users.username` is lowercase `[a-z0-9_]{3,20}` (any case accepted, normalised; reserved words blocked; change once per 30 days). `usernameService` (`username-service.ts`) keeps a username → id map in memory, loaded at boot, as a fast pre-check and for exact-match lookups; the unique index is the real guard (single API instance assumed). Login accepts email or username (`@` ⇒ email). Tagging (`POST /api/people/link`, exact username, no search) creates a `people` row with `linked_user_id`; the tagged user sees it under Split & share → Shared with me (`GET /api/splits/shared`) and, per their `tagged_expenses` setting (`manual` by default, or `auto`) or per-split decision (`shared_split_prefs`), gets a debit copy (`transactions.shared_split_id`, "Shared expenses" category, default account) kept in sync by `syncSharedTransactions`. Deleting that copy records "don't add". Users can block a username from tagging them (`user_blocks`). Balances/settlements stay owner-only.
- Storage & attachments (`storage-service.ts`, `attachment-service.ts`, `attachments-controller.ts`): files live in a PRIVATE Cloudflare R2 bucket through Bun's `S3Client` (`S3_*` env; without it they go to `LOCAL_STORAGE_DIR` on disk). Nothing is public: `storageService.serve()` answers with a 302 to a 5-minute signed URL, and only from routes that checked access (`/api/attachments/:id/file`, `/api/public/shares/:token/attachments/:id/file`); storage keys never reach the web. A transaction takes up to 5 files of 10 MB (JPG, PNG, WebP, PDF; the type is sniffed from the bytes, never trusted from the upload), 500 MB per user. Uploads go through the API as multipart (prod nginx has `client_max_body_size 100M` on `/api/`). Images are re-encoded on upload with `Bun.Image` to WebP quality 80, longest side 2560px (`compressImage`), so every stored image is `image/webp`; PDFs are stored as sent. `attachments.transaction_id` is `on delete set null`, and `sweepOrphanAttachments` (hourly + after a transaction delete) removes those rows and their files, so transaction deletes need no storage code. Lists show `attachmentCount`.
- Share links (`shares-controller.ts`, `share-service.ts`, web `/s/$token`): `book_shares` is a public read-only link to one book (optional from/to dates for the expenses shown, where payments received after the to-date still count; expiry date, message, password, UPI ID, `attachments` shown/hidden). `publicSharesController` is mounted outside `userControllers` and never returns account names. A password is checked once, then an httpOnly cookie `share_<id>` (HMAC of the link's `secret` over its password hash, path `/api/public/shares`) unlocks it; changing or removing the password rotates `secret`. A `separate` book shows spent, paid back and due; other books only their expenses. The page builds a `upi://pay` link + QR (`upiLink`) for the due amount. "Mark as paid" on a book is just a prefilled credit for the outstanding amount; a book is "Paid" when `outstanding <= 0`, there is no settled column. "I've paid" on the public page (`POST /api/public/shares/:token/claims`, rate-limited, max 10 pending per link) only inserts a `payment_claims` row (`status` pending/confirmed/dismissed + `decided_at`); it never touches money. The owner sees pending ones on the book page (`books.pendingClaims`) and confirms (`POST /api/shares/claims/:id/confirm`, creates the credit in that book, "Refund" category, chosen or default account) or dismisses.
- Transactions page (`routes/_app/transactions.tsx`): one period at a time, picked from the mode menu: `?period=day|week|year|all` (absent = month, `all` = everything) and `?date=yyyy-MM-dd`, the period's first day (absent = the one today is in); weeks are Monday–Sunday; a `from`/`to` range wins over both. A year charts a bar per month, shorter periods a bar per day, and a bar opens that month or day, numbered pages of `TXN_PAGE_SIZE` (100, the API's max `limit`) that only show when a period has more. The card on top (`PeriodSummary`) comes from `GET /api/transactions/summary` (`summarizeTransactions`), which uses the list's own `txnWhere` filters, so it always adds up to what is listed (every book unless one is picked, unlike Reports). Other screens still use the infinite `useTransactions`.
- Offline & sync (`apps/web/src/lib/offline/`): local-first like Docs/Figma. The TanStack Query cache is saved to IndexedDB (`idb.ts`, `PersistQueryClientProvider`, busted per build via `__APP_VERSION__`), so screens open with their last data offline. Daily-entry writes (transactions, transfers, splits, settlements) never call the API directly: the hooks call `queue*` in `sync.ts`, which adds an op to the outbox (`outbox.ts`, zustand persisted to IndexedDB, files included), patches every cached list/total/balance at once (`optimistic.ts`, rows made offline have negative temp ids and `_sync: "pending"`), and `flush()` sends ops in order, maps temp ids to real ones, retries network/5xx with backoff, parks refusals as "failed" in the sync panel (retry/discard), then refetches. Fresh server data has still-pending ops replayed on top (`overlayPending`). Creates send `clientId` (the op id; unique per user on `transactions`/`transfers`/`splits`/`settlements.client_id`) so a retry never duplicates; transaction PATCH and split PUT take `baseUpdatedAt` + `editedAt` and the latest edit wins (`lib/utils/sync.ts`: 409 + current row when the other device's change is newer, `replaced` in the response when ours is; the web offers "Use mine" / "Restore theirs"). Other writes (accounts, books, budgets…) still need a connection. Logout or a different user wipes IndexedDB (`forgetDevice` / `claimDevice`). Pages must prefer cached `data` over `error`.
- Drafts: form state for the transaction and split sheets lives in `stores/draft-store.ts` (`useDraft`, IndexedDB), keyed `txn:new` / `txn:<id>` / `split:…`, so closing a sheet by accident keeps the input; it is cleared on save, and an edit draft is dropped if the row's `updatedAt` changed.
- Keyboard shortcuts: actions, defaults and validation are in `apps/api/src/lib/utils/shortcuts.ts`, imported by both apps (`$/lib/utils/shortcuts`). Resolved as code defaults → admin's `SYSTEM_CONFIG.SHORTCUTS.DEFAULTS` (exposed in `/api/auth/config`) → the user's `users.shortcuts` (only differences stored, `PATCH /profile`). Bindings that the OS/browser own (most ⌘/Ctrl+key, any Alt, bare Enter/Esc/Tab/arrows) and clashes are refused on both sides. Global listener: `useGlobalShortcuts` (`hooks/use-shortcuts.ts`), handlers in `app-shell.tsx`; plain keys are ignored while typing or with a dialog open. A new action needs an entry in `SHORTCUT_ACTIONS` and a handler.
- PWA: hand-written `apps/web/public/manifest.webmanifest` (with app shortcuts `?new=debit|credit`); vite-plugin-pwa only generates the service worker (precached app shell, `registerType: "prompt"`), registered in `lib/pwa.ts`, which also keeps the `beforeinstallprompt` event for the one-click "Install app" (iOS gets Add-to-Home-Screen steps). The desktop sidebar collapses (`stores/ui-store.ts`, `[`).
